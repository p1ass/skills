# Code Reviewer

Google's Code Review Guidelines に基づき、複数の専門観点から並列にコードレビューを実施する。

レビューの目的は「コードベースの健全性を時間とともに改善すること」にある。欠点のないコードを求めるのではなく、変更がコードベース全体の品質を確実に向上させているかを検証する。

## ワークフロー

### Step 1: コンテキストの把握

レビュー対象を特定し、変更の背景を理解する。背景を理解せずに差分だけ見ると、設計意図を見落とす。

1. PR 番号やブランチ名から対象を特定する
2. PR の説明文、関連する Issue・チケットがあれば読む
3. `git diff` または `gh pr diff` で差分を取得する
4. 変更されたファイルの一覧と変更量を俯瞰する
5. 変更量が多い場合は、ファイルをリスク順にトリアージする（ビジネスロジック > インフラ/設定 > テスト > 生成コード）

```bash
# PRの差分を取得
gh pr diff <PR番号>

# ブランチ間の差分を取得
git diff <base-branch>...HEAD --stat
git diff <base-branch>...HEAD
```

### Step 2: 変更ファイルの文脈理解とコードベース調査

差分だけでは変更の影響範囲を正しく判断できない。変更されたファイルの全体像と、関連するコードベースを積極的に調査する。このステップを省略すると、既存コードとの不整合や影響範囲の見落としに直結する。

1. **変更ファイルの全文読み込み**: 変更が大きいファイル（特にビジネスロジック）は差分だけでなくファイル全体を読む。差分の前後にある既存コードの文脈が、変更の妥当性判断に不可欠
2. **呼び出し元・呼び出し先の調査**: 変更された関数・メソッドの呼び出し元と呼び出し先を `grep` で特定する。変更が上流・下流にどう影響するかを把握する
3. **同パッケージ・同レイヤーの関連ファイル調査**: 型定義、インターフェース、同レイヤーの類似実装を確認する。新しいコードが既存のパターンや共通処理と整合しているかを検証する
4. **類似機能の既存実装確認**: 似た機能が既に実装されている場合、そのパターンとの一貫性を確認する。重複実装がないかも調べる
5. **プロジェクトの言語を特定する**（Go, TypeScript, Python 等）

```bash
# 変更された関数の呼び出し元を調査
grep -rn "functionName" --include="*.go" .

# 同パッケージの関連ファイルを確認
ls -la path/to/package/

# 類似パターンの既存実装を検索
grep -rn "SimilarPattern" --include="*.go" .
```

### Step 3: 並列レビューの実行

以下の 6 観点について、それぞれ専門の subagent を**並列で**起動する。各 subagent には差分情報と変更ファイルのパスを渡す。

subagent 起動時、各 agent に以下の情報を含めること:
- レビュー対象の差分（diff の全文、またはファイルパスと PR 番号）
- 変更されたファイルの一覧
- プロジェクトのルートパス
- PR の説明文や背景情報（あれば）
- プロジェクトの主要言語
- このスキルのパス（agent 指示ファイルの参照に必要）
- **差分だけでなく、変更ファイルの全文や関連ファイル（呼び出し元/先、同パッケージの型定義、類似機能の既存実装）を積極的に読み込むこと**の指示

#### 起動するsubagent

各 subagent の指示は `agents/` ディレクトリにある。起動時に該当する agent 指示ファイルを読むよう指示すること。

| 観点 | Agent指示ファイル | 目的 |
|---|---|---|
| 設計 | `agents/design.md` | アプローチの妥当性、アーキテクチャとの整合性 |
| 正確性 | `agents/correctness.md` | バグ、エッジケース、エラーハンドリング |
| セキュリティ | `agents/security.md` | 脆弱性、入力検証、情報漏洩 |
| パフォーマンス | `agents/performance.md` | 構造的なボトルネック、計算量の問題 |
| 一貫性 | `agents/consistency.md` | 命名規則、設計パターン、可読性 |
| テスト | `agents/testing.md` | テストカバレッジ、テスト品質 |

subagent 起動のプロンプト例:

```
以下のPRの変更を「{観点名}」の観点からレビューしてください。

まず {スキルパス}/agents/{観点}.md を読み、レビュー指示に従ってください。
Goプロジェクトの場合は {スキルパス}/references/go-review-guideline.md も参照してください。

## レビュー対象
- PRの説明: {PR説明}
- 変更ファイル一覧: {ファイルリスト}
- プロジェクトルート: {ルートパス}
- 主要言語: {言語}

## 差分
{diff全文}

差分だけでなく、変更されたファイルの全文や関連ファイルも必要に応じて読んでください。
確信度の高い指摘のみ報告してください。
```

### Step 4: 結果のマージと出力

すべての subagent の結果を収集し、以下の手順で最終出力を作成する。

1. **重複排除**: 複数の subagent が同じ箇所を指摘している場合は統合する
2. **重要度順に並べ替え**: 以下の優先度で整理する
3. **良い点の集約**: 各 subagent が報告した良い設計判断を「良い点」セクションにまとめる

#### 重要度の順序

1. **設計上の問題** — 最優先。アプローチ自体の再考が必要
2. **機能の不具合** — バグやエッジケースの見落とし
3. **セキュリティ** — 脆弱性や情報漏洩のリスク
4. **パフォーマンス** — 構造的なボトルネック
5. **可読性** — コードの理解しやすさ
6. **スタイル** — 一貫性の問題

#### ラベル

各指摘の先頭にラベルを付与し、対応の緊急度を明示する。

| ラベル | 用途 |
|---|---|
| **must** | 修正必須。マージ前に対応が必要（バグ、セキュリティ、設計上の欠陥） |
| **should** | 修正推奨。対応が望ましいが、理由があれば見送り可 |
| **nits** | 些末な指摘。対応は任意（命名の微調整、コメントの改善） |
| **question** | 質問・確認。意図や背景の確認 |
| **suggestion** | 改善提案。より良いアプローチの提示 |

#### 出力フォーマット

```markdown
## Code Review

対象: [PR番号 or ブランチ名]
変更ファイル数: [N]
レビュー観点: 設計 / 正確性 / セキュリティ / パフォーマンス / 一貫性 / テスト

### 総評

[変更全体に対する1-2文の評価。設計上の問題があれば先に明記する]

### 良い点

- [優れた設計判断や工夫があれば記載]

### 指摘事項

#### [must] エラーが握りつぶされている
- 観点: 正確性
- 箇所: `path/to/file.go:42`
- 問題: `err` が返されずに無視されている。このエラーが発生した場合、後続の処理が不正なデータで続行される
- 改善案: `err` を呼び出し元に返す。ログ出力だけでは不十分

#### [should] 不要なデータベースクエリ
- 観点: パフォーマンス
- 箇所: `path/to/service.go:85-92`
- 問題: ループ内で毎回クエリを発行しており、N+1問題が発生する
- 改善案: ループ外で一括取得し、mapで参照する

#### [nits] 変数名の改善
- 観点: 一貫性
- 箇所: `path/to/handler.go:15`
- 問題: `d` は意図が不明確
- 改善案: `duration` に変更
```

## レビューの原則

- **建設的に伝える**: 問題の指摘だけでなく、具体的な改善案を提示する。「ダメ」ではなく「こうすればより良い」と伝える
- **理由を添える**: 指摘の根拠を示す。「なぜダメなのか」が分からない指摘は受け入れにくい
- **良い点も認める**: 優れた設計判断や工夫が見られる場合は積極的に言及する。レビューは問題を見つけるだけの場ではない
- **完璧を求めない**:「この変更がコードベースを改善しているか」が判断基準。レビュアーの好みを押し付けない
- **確信度の低い指摘は出さない**: 推測に基づく指摘はノイズになる。コードを実際に読んで裏取りした上で指摘する
