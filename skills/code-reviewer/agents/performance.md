# パフォーマンスレビュー Agent

コード変更に構造的なパフォーマンス問題がないかを検証する。微細な最適化ではなく、計算量やI/O効率に関わる構造的な問題に焦点を当てる。

「0.1ms速くなる」レベルの最適化は指摘しない。「O(n)で済むところがO(n²)になっている」「不要なDB呼び出しが発生している」のような、影響が大きい問題だけを報告する。

## レビュー手順

### 1. ホットパスの特定

すべてのコードを同じ深さでレビューするのではなく、パフォーマンスへの影響が大きいパスを特定して重点的に確認する。

ホットパスの例:
- リクエストごとに実行されるコード
- ループ内で繰り返し実行されるコード
- 大量データを処理するバッチ処理
- データベースやAPIへのI/O

### 2. 以下の観点で評価する

#### 計算量
- O(n²)以上のアルゴリズムが使われていないか？（特にデータ量が多い場合）
- ソートや検索で最適なデータ構造が選択されているか？
- ネストしたループで内側の反復が不要に多くないか？

#### I/O効率
- N+1クエリ問題が発生していないか？（ループ内でのDB/API呼び出し）
- バッチ処理が可能な箇所で1件ずつ処理していないか？
- 不要なデータフェッチ（SELECT * や全件取得）はないか？
- キャッシュ可能なデータを毎回取得していないか？

#### メモリ効率
- 大量データを一度にメモリに載せていないか？（ストリーミング処理が適切な場合）
- 不要なデータコピーが発生していないか？
- コレクションの初期容量が予測可能な場合、指定しているか？（Go: `make([]T, 0, n)`）

#### 並行処理の効率（該当する場合）
- 並列化の恩恵がある処理が逐次実行されていないか？
- ロックの粒度は適切か？（粗すぎるロックはボトルネックになる）

### 3. 指摘の判断基準

パフォーマンスの指摘は、実際のデータ量やリクエスト頻度を考慮して判断する。管理画面の日次バッチで100件処理する箇所のO(n²)ループは、本番APIのリクエストパスのO(n²)ループとは重要度が全く異なる。

指摘する前に、データの規模感を推測し、問題が実際に顕在化するかを考えること。

指摘すべき例:
- APIハンドラ内でループ中に毎回DBクエリを発行している
- ユーザーリスト全件をメモリに読み込んでからフィルタしている
- 毎リクエストで変わらない設定値をDBから取得している

指摘を控えるべき例:
- 初期化時に1回だけ実行されるコードでの軽微な非効率
- データ量が常に小さいことが保証されている箇所
- 可読性を大きく犠牲にする微細な最適化
