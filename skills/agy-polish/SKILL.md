# Agy Polish

`agy` (Antigravity CLI) を使用して日本語文章を推敲する。モデルは表現力の高い `gemini-3.8-flash-high` で固定する。

## Step 1: 対象ファイルの特定

- ファイルパスが指定された場合: 指定されたファイル
- 引数が渡されなかった場合: `git status` を実行し、変更中の `.md` / `.mdx` / `.txt` ファイルを特定する（複数存在する場合はユーザーに確認する）

対象ファイルのパスは必ず絶対パスへ解決する。以降、対象ファイルを含むリポジトリのルート（Git 管理外ならファイルのディレクトリ）を「ルート」と呼ぶ。

## Step 2: プロジェクトのルールと Linter の確認

推敲時に従わせるルールと、推敲後に実行する Linter を決める。

- **ルールファイル**: ルートに `AGENTS.md` または `CLAUDE.md` があれば、そのパスを控える。両方ある場合は `AGENTS.md` を優先する。
- **Linter**: ルートに `.textlintrc*` があり、`textlint` がインストールされている場合は `pnpm exec textlint <絶対パス>` を使う（パッケージマネージャーはロックファイルに合わせて `npx` などに読み替える）。それ以外の場合は Linter を使わない。

## Step 3: バックアップの作成

未コミットの下書き状態でも差分を正しく確認できるよう、推敲前のファイルを一時ディレクトリへ複製しておく。スクラッチパッドがあればそこを使う。

```bash
cp -f "<絶対パス>" "<一時ディレクトリ>/before-<ファイル名>"
```

## Step 4: agy による推敲の実行

Step 2 の結果に応じてプロンプトを組み立てる。基本形は次のとおり。

```text
<絶対パス> のファイルを日本語として自然に推敲し、上書き保存してください。事実関係や技術的な意味は変えず、frontmatter、コードブロック、URL、HTML/MDX のタグ、コメントは変更しないでください。ファイルの読み書きは組み込みのファイル操作ツールで行い、シェルコマンドは実行しないでください。
```

- ルールファイルがある場合: 冒頭に「`<ルールファイルの絶対パス>` を読み、そのルールに従って」を加える。
- Linter がある場合: 末尾に「その後 `<Linter コマンド>` の指摘がなくなるまで修正してください」を加え、シェルコマンドの禁止に「`<Linter コマンド>` 以外」という例外を付ける。

ルートで以下のコマンドを実行する。推敲には数分かかる場合があるため、Bash のタイムアウトは 10 分（600000 ms）に設定する。

```bash
agy -p "<プロンプト>" \
  --model gemini-3.8-flash-high \
  --mode accept-edits \
  --add-dir "<ルート>" \
  --add-dir "<対象ファイルのディレクトリ>" \
  --print-timeout 9m
```

`--mode accept-edits` と `--add-dir` は必ず指定する。`--add-dir` には、ルールファイルと対象ファイルの両方を読み込めるディレクトリを指定する。指定しない場合は headless モードでファイルの読み書き権限が自動的に拒否され、ファイルが更新されないまま正常終了する。実行後にファイルが変更されていない場合は、出力ログに Permission エラーが含まれていないか確認する。

agy 内で Linter を実行するには、`~/.gemini/antigravity-cli/settings.json` に権限を追加する必要がある。`command` の権限エラーで停止した場合は、ユーザーに次の設定の追加を依頼する。

```json
{ "permissions": { "allow": ["command(pnpm exec textlint)"] } }
```

## Step 5: 差分の検証

以下のコマンドを実行して差分を確認する。Linter がある場合はあわせて実行する。

```bash
git diff --no-index --word-diff "<一時ディレクトリ>/before-<ファイル名>" "<絶対パス>"
```

変更箇所を 1 箇所ずつ確認し、以下のいずれかに該当する疑いのある変更を洗い出す。この時点ではファイルを元に戻さない。

- ルールファイルのルールに違反している
- 事実関係や意味・ニュアンスが変わっている
- 文章以外の要素に影響が及んでいる
- 元の文章の文体から外れている

プロジェクトに執筆ガイドがある場合は、それも判断基準に加える。Linter の指摘が残っている場合は手動で修正する。

## Step 6: ユーザーによる判断

主な変更点を簡潔に要約したうえで、Step 5 で洗い出した変更ごとに変更前後の文と懸念点をユーザーに提示し、元に戻すかどうかを確認する。ユーザーが元に戻すと判断した変更のみを元に戻す。
